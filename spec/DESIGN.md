# Design system: tokens and state styles

Turns `GLOSSARY.md` (state names) into concrete tokens and per-state styles for `crittable/`. All values here are our own. The single source is the `TOKENS` and `SCALE` objects at the top of the stylesheet in `crittable/pinwall.js`; they are emitted as CSS custom properties `--cm-<name>` on every shadow host. Components only reference `var(--cm-*)`, so a palette change is one edit.

Our own pages outside the tool (the docs page, `index.html`) read the same tokens from `site/tokens.css`, generated by `scripts/export_design_system.js` and checked for staleness with the rest.

Live views: `sample/index.html` (the tool on a stand-in page) and `sample/states.html` (every glossary state as a static specimen, made by the product's own builders, which `pinwall.js` hands to the sheet as `kit.parts`, and drawn by the real stylesheet; `?theme=light` or `?theme=dark` for one theme, no parameter for both side by side).

## 0. Theme mechanism

- `:host` carries the light set. `:host([data-theme=dark])` carries the dark set. `@media (prefers-color-scheme: dark) { :host(:not([data-theme=light])) }` also applies the dark set.
- Default theme is `auto`: no attribute, so the OS preference decides through the media query and no JS listener is needed. The override is stored in the settings record as `theme` (`auto` | `light` | `dark`; initial value from `CRITTABLE_CONFIG.theme`). It is set as `data-theme` on **every** shadow host (main and the new-note editor host), so the override beats the OS and all surfaces flip together.
- UI: More menu, one row (`MENU.Theme`): a press steps Light, Dark, Match system, in that order, and the menu stays open. The row shows a sun, a moon or a screen and names the choice at its trailing edge. On a step the old sign sets and the new one rises (`cm-set`, `cm-rise`, `medium`, `ease`): the old one drops straight down and the new one comes straight up, inside a box that clips at the horizon. The colours fade across over `medium` while the step happens (`.theming`), so the panel does not flash.
- The wash on a target (target hint, open note, row click) is a box in the shadow root, positioned over the target each frame; the host element's own styles are never written. Its colour is `pin-wash`, fixed in both themes (brand rule 3).

## 1. Colour roles

Values are not repeated here. They live in `TOKENS` and `SCALE` in `crittable/pinwall.js` and are published, with a usage note each, in `design-system/project/tokens.json`.

| Token | Role |
|---|---|
| `base` | Base surface: panel |
| `raised` | Raised: launcher, pins, cards |
| `hover` | Hover surface |
| `overlay` | Menus, new-note bar |
| `input` | Field fill |
| `strip` | Tinted bands (composer strip, delete confirmation) |
| `selected` | Selected wash, quoted words |
| `accent-wash` | Active menu choice, open trigger |
| `halo` | Halo outside a focused field |
| `text` / `text-author` / `text-body` / `text-meta` / `text-hint` | Text ladder (4 steps plus author) |
| `border-hair` / `border` / `border-emph` | Divider, container, emphasis |
| `control-edge` | The edge of a field or an unfilled button. Ink in light, the same as `accent-edge`, so a field and the yellow button beside it are edged alike; soft in dark, where the yellow button has no edge. Rule: what you can act on has an ink edge, structure stays pale |
| `accent` | Highlighter. **Only ever a fill behind ink**, never text or a thin line on a light surface |
| `accent-ink` | Links, unread dot, checked controls |
| `accent-deep` | Send / button hover |
| `accent-edge` | 1px edge under an accent fill |
| `focus` | Focus ring, focused field border |
| `card-edge` | Hairline round every floating card |
| `on-accent` | Glyph and text on accent |
| `ok` `warn` `err` `info` `neutral` | Semantic. Warn is orange so it cannot be read as the accent |
| `on-err` | Text on error fill |
| `done` / `on-done` | Resolved control fill / its check |
| `send-off` / `send-off-ink` | Disabled send |
| `shade` / `shade-a` | Shadow ink and base alpha |

Hint text keeps at least 4.5:1 on its surface in both themes.

**Avatar palette** (six colours, chosen by a hash of the name shown, lower-cased, so one name is one face everywhere, none near the highlighter yellow): a face is a pale wash of the person's colour with initials in the deep shade of the same colour, never a flat saturated disc (a flat disc read as hard-edged beside the paper). In a pin it is `av-N` under `av-N-ink`, the same in both themes because a pin sits on the host page. In a card or the panel it is `face-N` under `face-N-ink`: the same pair in light, reversed in dark (a dusk of the colour under its pale wash). Every pair clears 4.5:1. When the author has an avatar image (`authorAvatar`, taken from `CRITTABLE_USER.avatar`, an `https:`, `data:image/` or relative URL the host page supplies) it covers the initials; the initials stay underneath as the fallback. The tool itself never fetches from a third party, with one opt-in exception: with `gravatar: true` in the config and no `avatar` given, the image URL is built from the SHA-256 of the person's address (`emailHash`, or `email` hashed in the browser) and requested from gravatar.com with `d=404`, so a missing one falls back to initials. The address itself is never stored.

**Fixed colours** (`pin-ink`, `pin-paper`, `pin-ring`, `pin-drop`, `pin-wash`): pins, the launcher, the undo toast and the wash on a target use these in both themes. They sit on the host page, and the OS theme says nothing about how bright that page is.

## 2. Scale tokens (theme-independent)

| Group | Tokens |
|---|---|
| Spacing | `s1` to `s6`, in steps of four |
| Radii | `r-sm` (icon buttons), `r-md` (inputs, rows, menu items, buttons), `r-lg` (cards, menus, panels), `r-tip` (the one sharp corner of a pin or card: it marks the anchor), `r-full` (avatars, list button) |
| Type | `font` system stack; `fs-face` (initials in a face only), `fs-meta`, `fs-body`, `fs-head`, `fs-type` (what is typed into a field on a touch device: 16px, so the phone does not zoom the page); `fw-regular`, `fw-strong`; `lh` |
| Elevation | `elev-1` (small raised parts), `elev-2` (the preview), `elev-3` (cards, menus, composer), `elev-edge` (sidebar edge): built from `shade`/`shade-a`, so dark is deeper and light softer. Parts on the host page use the fixed `pin-drop` and `pin-lift` instead, in both themes |
| Motion | `fast` (hover, press, fades), `medium` (cards, panel, menus), `linger` (only the warning fade-out), `instant`; `ease` for everything. One signature move: `cm-plant`, the draft pin dropping onto its spot. Every wait in the JavaScript is named in the `TIME` table in `pinwall.js`, whose motion entries are computed from these tokens; the smoke test rejects a literal delay. What each is for is in the Motion table in `GLOSSARY.md` section 12 |
| Layers | `z-dock` < `z-card` < `z-panel` < `z-banner`; pins sit just above their target's stacking context |

Values are in `tokens.json`, not here.

Reduced motion: `@media (prefers-reduced-motion: reduce)` sets every animation and transition to none (instant). The card leave tween is skipped in JS as well.

Forced state classes: every hover, press or focus pseudo-class style is paired with `.is-hover`, `.is-pressed` or `.is-focus`, so the state sheet can show it without a pointer.

| `EMPTY.StorageFailed` | `.note-banner` / `.err` / `aside.fail` | the page banner (`.note-banner`) is `pin-ink` with `pin-paper` text and a `pin-ring`, fixed in both themes because it sits on the host page; inside a card or the panel it is a quiet line in `err`; never a modal | `fast` fade |

Every colour-only cue is paired with a glyph or text: check glyph for resolved, a dot plus screen-reader text for unread, and the reason text for muted rows.

## 4. Rules for new work

1. No colour literals in components. Add a role token to both theme sets first. The accent is a fill: never use it for text or a 1px line on a light surface; use `accent-ink` or `focus`, which are ink in light and yellow in dark.
2. Only `fast`, `medium` and `instant` (plus `linger` for the warning fade). Type sizes, weights and radii come from tokens too. The smoke test fails on a new literal; the few existing ones are baselined in `smoke_test.py`.
3. A new state needs a name in `GLOSSARY.md`, a row here, and a specimen in `sample/states.js`.
